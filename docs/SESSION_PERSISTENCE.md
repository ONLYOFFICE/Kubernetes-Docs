# Session persistence for HTTP long-polling

By default, the editors connect to ONLYOFFICE Docs over WebSocket. If a WebSocket connection cannot be established (for example, it is blocked by a proxy or firewall), the editors automatically fall back to HTTP long-polling.

With HTTP long-polling, one co-editing session consists of a series of separate HTTP requests with the same session ID (`sid`). The session is stored in the memory of the `docservice` Pod that accepted the handshake. If `docservice.replicas` is greater than `1` or `docservice.autoscaling.enabled=true`, requests of one session may be routed to different Pods and fail with `400 Bad Request` and the `Session ID unknown` message.

To avoid this, configure session persistence on the component that exposes ONLYOFFICE Docs: the Gateway, the Ingress controller, or the cloud load balancer.

The recommended method is consistent hashing by the `shardkey` query parameter: the editor adds it to every co-editing request, so all users of the same document are served by the same `docservice` Pod. Requests without `shardkey` (static files, health checks) are balanced using round-robin. This method does not depend on cookies, so it also works when ONLYOFFICE Docs is embedded into a document management system on a different domain and third-party cookies are blocked by the browser.

When a `docservice` Pod is removed (scale down, rolling update, failure), the sessions served by this Pod are reconnected automatically to another Pod, and the editors show the *Connection is restored* message.

**NGINX Gateway Fabric**

Set the `gateway.upstreamSettingsPolicy` parameter. The chart creates an `UpstreamSettingsPolicy` attached to the ONLYOFFICE Docs Service:

```yaml
gateway:
  enabled: true
  upstreamSettingsPolicy:
    loadBalancingMethod: "hash consistent"
    hashMethodKey: "$arg_shardkey"
```

**F5 NGINX Ingress Controller**

Use only one of the two options below.

Option 1. Consistent hashing by the document shardkey (recommended)

```yaml
ingress:
  annotations:
    nginx.org/lb-method: "hash $arg_shardkey consistent"
```

Option 2. Sticky cookie 

Binds a browser to a `docservice` Pod using a cookie generated by NGINX

```yaml
ingress:
  annotations:
    nginx.org/sticky-cookie-services: "serviceName=documentserver DOCSRV expires=1h path=/"
```

`serviceName` must match the ONLYOFFICE Docs Service name (`documentserver` by default, or the value of `service.existing`). If ONLYOFFICE Docs is embedded into a page on a different domain, add `samesite=none secure` to the cookie parameters. Such cookies are accepted by browsers over HTTPS only and may still be blocked when third-party cookies are disabled; in this case, use Option 1.

**Service of type LoadBalancer**

If ONLYOFFICE Docs is exposed via a Service of type `LoadBalancer` (see [here](../README.md#531-expose-onlyoffice-docs-via-service-http-only)), the cloud load balancer selects a cluster node for each new connection. Session persistence must therefore be provided by the cloud load balancer itself. Refer to your cloud provider documentation for sticky sessions and add the required annotations using the `service.annotations` parameter.

If the cloud load balancer binds a client to a node rather than to a Pod, make sure the node forwards the requests only to its own `docservice` Pod:

- set `service.externalTrafficPolicy: Local`. Requests are not forwarded to Pods on other nodes, and nodes without a `docservice` Pod fail the load balancer health check (`healthCheckNodePort`), if your cloud provider uses it;
- run no more than one `docservice` Pod per node (`podAntiAffinity.type: "hard"`). With autoscaling, `docservice.autoscaling.maxReplicas` must not exceed the number of nodes available for `docservice`, otherwise the extra Pods stay `Pending`.

> **Note**
>
> By default, F5 NGINX Ingress Controller and NGINX Gateway Fabric route traffic directly to the Pod endpoints, and external load balancers distribute connections across the cluster nodes.
>
> `service.sessionAffinity: ClientIP` alone may not be sufficient: it does not control which node the cloud load balancer selects. `service.externalTrafficPolicy: Local` preserves the client source IP for network load balancers, but does not make the load balancer sticky either.
